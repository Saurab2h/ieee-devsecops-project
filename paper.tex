\begin{abstract}
Security validation in continuous integration and continuous delivery (CI/CD) pipelines is, in most industrial practice, applied post-hoc, leaving vulnerabilities to be discovered by penetration testers or attackers rather than by the pipeline itself. This paper presents a systems experience report and case study of a five-layer DevSecOps pipeline, built as an M.Tech academic project (P07) at IIIT Bangalore, that embeds static application security testing (SAST) with Semgrep, software composition analysis (SCA) with OWASP Dependency-Check, container vulnerability scanning with Trivy, Policy-as-Code gates implemented in Open Policy Agent (OPA) and Rego, and dynamic application security testing (DAST) with OWASP ZAP directly into a Jenkins declarative pipeline. The pipeline was evaluated against three deliberately vulnerable target applications -- vulnapp, DVWA, and OWASP Juice Shop -- spanning a range of base-image staleness and vulnerability density. Three research questions guide the case study: the velocity cost of embedding security tooling, the dynamics of container vulnerability exposure across application types, and the relative efficacy of Policy-as-Code versus imperative Bash scripting. On our single-host Jenkins environment, the synchronous pipeline adds approximately 23 seconds over a 206-second unsecured baseline (Table~\ref{tab:timings})---a whole-pipeline delta that sits within the baseline's measurement variance and therefore should not be presented as a statistically clean estimate of security-induced overhead. Relying instead on the per-stage decomposition, ZAP is identified as the dominant latency contributor; decoupling it to an asynchronous job reduces developer-blocking overhead to under 15 seconds, a multiplier below approximately 1.07$\times$ over the 206-second baseline. Across the three applications, the Configuration and Severity gates blocked all observed non-compliant deployment attempts, while the Provenance Gate blocked vulnapp based on 27 dual-scope CVEs and passed the other two applications (Table~\ref{tab:opa_gates}). In a controlled $N=30$ benchmark on our local host, OPA policy evaluation showed a 42.8\% lower mean evaluation latency than an equivalent Bash-and-jq implementation while producing structured JSON output; in the two-rule comparison, the Bash implementation increased from 11 to 24 LOC, whereas the Rego implementation increased from 40 to 43 LOC, suggesting more favorable scaling (Table~\ref{tab:gate_benchmark}). An inner-team annotation exercise by both developers on 50 randomly sampled Trivy findings yielded Cohen's Kappa $\kappa = 0.660$ (Substantial Agreement), serving as a reliability check on the manual verification of automated severity classifications in our sample. These findings are mapped onto the three research questions in Sections~\ref{sec:results} and~\ref{sec:conclusion}.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Software delivery pipelines have compressed the interval between a code commit and a production deployment from weeks to minutes, but the security validation performed within that interval has not kept pace with this compression. In many organizations, security review still happens outside the pipeline entirely: a manual penetration test scheduled quarterly, a compliance checklist filled out after release, or a code review that focuses on functional correctness rather than exploitability. Where automated tooling exists, it is frequently limited to a single scanner invoked as an advisory step whose failure does not block the build, or to a hand-rolled Bash script that parses a JSON report with \texttt{jq} and exits non-zero on a hard-coded threshold. Both patterns leave a gap between the moment a vulnerability is introduced into a codebase or container image and the moment it is discovered, and neither produces a machine-readable, queryable record explaining why a given build was allowed to proceed to deployment.

This gap motivates the central question addressed by this paper: can a multi-stage DevSecOps pipeline enforce security policy across the software supply chain with acceptable velocity cost, and does encoding that policy declaratively using Open Policy Agent (OPA) and Rego offer advantages over imperative Bash scripting? To answer this question we designed, implemented, and instrumented such a pipeline as an M.Tech academic project (P07) at IIIT Bangalore, titled \emph{Automated Multi-Stage DevSecOps Pipeline with Policy-as-Code Enforcement Using OPA and Jenkins}. This paper presents an experience report and case study of that implementation: all measurements are single-host, environment-specific benchmarks intended to characterize relative stage costs and design trade-offs, not to be read as generalizable population-level statistics. The study is organized around three research questions.

RQ1 asks what the quantified security-versus-velocity cost is of embedding multi-stage security tooling into a CI/CD pipeline. RQ2 asks how container vulnerability profiles differ across application types, and whether base-image staleness dominates CVE exposure. RQ3 asks whether Policy-as-Code, implemented with OPA and Rego, provides measurable advantages over equivalent Bash scripting in a DevSecOps gate.

The contributions of this experience report are fivefold. First, we present a fully scripted Jenkinsfile embedding SAST, SCA, container scanning, and DAST behind three OPA policy gates for configuration, severity, and CVE provenance across three applications with distinct technology stacks and base-image ages. Second, we release an OPA policy bundle expressing OWASP Top~10-aligned checks in Rego, unit-tested with \texttt{opa test}. Third, we document a case study across three applications of differing base-image freshness and vulnerability density, allowing the vulnerability dynamics of RQ2 to be examined comparatively within our controlled environment. Fourth, we report repeated-measurement benchmarks with standard deviations and 95\% confidence intervals characterizing relative stage costs in our single-host environment. Fifth, we describe a Prometheus- and Grafana-backed observability layer giving the pipeline a persistent, queryable audit trail, a capability that a bare Bash exit-code gate structurally cannot provide.

The remainder of this paper is organized as follows. Section~\ref{sec:related} surveys related work on DevSecOps maturity models, empirical CI/CD timing studies, and Policy-as-Code tooling, and situates our pipeline against four existing operational approaches. Section~\ref{sec:arch} describes the five-layer pipeline architecture and the three OPA gates. Section~\ref{sec:setup} describes the experimental setup, target applications, and tool versions. Section~\ref{sec:results} presents the empirical results organized around the three research questions. Section~\ref{sec:discussion} discusses operational recommendations that follow from the results. Section~\ref{sec:validity} addresses threats to validity, including a dual-rater construct-validity study. Section~\ref{sec:conclusion} concludes the paper, maps each research question to its answer, and describes future work.

\section{Related Work and Comparative Study}
\label{sec:related}

\subsection{DevSecOps Maturity Models}
Maturity models such as the OWASP Software Assurance Maturity Model (SAMM) formalize the idea that security practices should be assessed and improved incrementally across the software development lifecycle rather than bolted on at release time~\cite{ref1,ref11}. These models motivate the shift-left principle underlying this work, in which security validation moves earlier into the development and build process, but they stop short of prescribing concrete pipeline mechanics or measuring the empirical cost of adoption, which is the gap this paper addresses through direct instrumentation.

\subsection{Empirical CI/CD Timing Studies}
A smaller body of work has measured CI/CD pipeline timing empirically rather than treating build duration as an afterthought~\cite{ref2,ref3}. These studies generally confirm that security or quality gates added synchronously to a pipeline measurably lengthen the feedback loop experienced by developers, but few decompose that cost stage-by-stage in the manner of Table~\ref{tab:timings} in this paper, and fewer still report confidence intervals across repeated runs rather than a single wall-clock measurement subject to host-level noise.

\subsection{SAST and SCA Complementarity}
Static application security testing (SAST) and software composition analysis (SCA) are frequently treated as substitutes in practitioner tooling comparisons, but they inspect fundamentally different artifacts: SAST reasons over first-party source code for insecure patterns, while SCA reasons over the declared and transitive dependency graph for known-vulnerable library versions~\cite{ref4,ref10}. The DAST findings summarized later in this paper, which surface HTTP-layer misconfigurations invisible to either SAST or SCA, reinforce that these tool classes are complementary rather than redundant, a theme developed further in Section~\ref{sec:results}.

\subsection{Container Scanning Landscape}
The container scanning landscape is dominated by a small number of open-source scanners that diff installed package manifests against vulnerability databases such as the National Vulnerability Database and distribution-specific security advisories~\cite{ref5,ref9}. Prior comparisons of these scanners focus primarily on detection recall; this paper instead uses one such scanner, Trivy, as a fixed measurement instrument and focuses on what its output reveals about \emph{where} CVEs originate -- the operating-system layer versus the application dependency layer -- which is the substance of RQ2.

\subsection{Policy-as-Code Landscape}
Policy-as-Code tooling, most visibly Open Policy Agent, proposes replacing imperative validation scripts with declarative policy evaluated by a general-purpose policy engine~\cite{ref6}. Existing discussion of OPA's advantages over scripted gates is largely qualitative, citing separation of policy from application logic and unit-testability of policy rules. This paper contributes a direct, controlled latency and lines-of-code comparison against an equivalent Bash-and-\texttt{jq} implementation, reported in Table~\ref{tab:gate_benchmark}, a controlled comparison that is uncommon in the existing literature.

Three observations follow from Table~\ref{tab:comparative_study}. First, vendor-hosted tools such as Snyk and the premium tiers of GitLab Auto DevOps lock teams into proprietary environments and dashboard licensing: their scanning logic and audit trail live in the vendor's infrastructure rather than the team's own version-controlled repository, and switching providers means discarding accumulated policy history rather than migrating it. Second, naive Bash gates rely entirely on tool exit codes to signal pass or fail, which fail to provide structured evidence for security compliance audits; an auditor asking why a specific build was permitted to deploy six months earlier has, at best, a console log to consult, and that log was never designed to be queried programmatically. Third, and most distinctively, the Provenance Gate implemented in our pipeline evaluates both the OWASP Dependency-Check output and the Trivy output simultaneously, correlating CVE identifiers in a single OPA process memory workspace rather than in two separate, uncoordinated tool invocations. This design ensures that source-manifest-level fixes and binary container-layer dependencies are verified together, within one policy evaluation, without requiring an external database or a second pass over previously scanned data. None of the three comparison approaches in Table~\ref{tab:comparative_study} performs this cross-tool correlation natively, and the Bash-and-\texttt{jq} baseline in particular is structurally ill-suited to it, since joining two independently structured JSON documents on a shared CVE identifier key, with correct handling of partial matches and differing identifier formats, is precisely the kind of relational logic that Bash's line-oriented text processing model handles poorly.

\section{System Architecture and Methodology}
\label{sec:arch}

The pipeline is implemented as a Jenkins declarative pipeline (Jenkinsfile) comprising five layers. Layer one is Semgrep-based SAST, which inspects first-party source code for insecure patterns before any container image is built. Layer two is OWASP Dependency-Check, an SCA stage that resolves the project's declared and transitive dependencies against known-CVE advisories. Layer three is Trivy, which scans the built container image's operating-system package manifest and application-layer dependency manifests for matching CVEs; because the pipeline evaluates all three target images in the same run, this stage is parallelized so that vulnapp, DVWA, and Juice Shop are scanned simultaneously rather than sequentially. Layer four consists of three independent OPA policy gates -- a Configuration Gate, a Severity Gate, and a Provenance Gate -- evaluated against the Trivy and Dependency-Check JSON output. Layer five is OWASP ZAP~\cite{ref8}, run in passive baseline mode against each running application container to surface HTTP-layer misconfigurations that static scanning cannot detect.

OPA sits deliberately between the scanning layers and the deployment step, rather than alongside them, because its role is to convert raw scanner output into a binding pass-or-fail decision with a recorded rationale. Three gates are evaluated in the pipeline. The Configuration Gate inspects \texttt{docker inspect} output for insecure runtime configuration, such as containers running as the root user or exposing privileged ports. The Severity Gate evaluates Trivy's JSON CVE report against configurable thresholds -- Critical findings greater than zero, High findings greater than ten, Medium findings greater than twenty-five -- and denies the build if any threshold is exceeded. The Provenance Gate, described in Section~\ref{subsec:comparative}, cross-references CVE identifiers appearing in both the Trivy container scan and the Dependency-Check SCA report simultaneously, within a single Rego evaluation. Any single gate failure halts the pipeline immediately and prevents the deployment stage from executing; the build is marked \texttt{BLOCK} and no image is promoted to the deployment target.

Observability is provided by a Prometheus and Grafana stack~\cite{ref7}, shown in Fig.~\ref{fig:grafana_dashboard}, that scrapes per-stage timing, CVE severity counts, and OPA gate verdicts from every pipeline run, giving the team a persistent time series rather than the transient console log a Bash script would leave behind.

\label{sec:setup}

Three deliberately vulnerable applications were selected as evaluation targets specifically because they span a wide range of technology stack, base-image freshness, and vulnerability density rather than representing a single application profile. Table~\ref{tab:targets} summarizes their characteristics.

vulnapp is a custom Spring Boot application built on \texttt{openjdk:8}, a base image whose upstream support ended in March 2022, and is deliberately seeded with OWASP Top~10 vulnerabilities. DVWA is built on \texttt{php:7.2-apache}, a base image whose upstream support ended in November 2020, considerably longer end-of-life than vulnapp's, and is included precisely to test the upper bound of operating-system-layer CVE accumulation under Trivy scanning. Juice Shop runs on \texttt{node:18-alpine}, an actively maintained long-term-support image, and is included as a contrast case in which any substantial CVE exposure must originate from its declared npm dependency tree rather than from base-image staleness.

Tool versions were held fixed throughout data collection to avoid cross-version variance confounding the timing and CVE-count results reported in this paper: Trivy, OPA, OWASP ZAP, Jenkins, and Docker were each pinned to a single version for the duration of the study, and all measurements were collected on a single host to avoid cross-host timing variance confounding the stage-timing results in Table~\ref{tab:timings}. Trivy stage timings were collected over $N=8$ runs per application; ZAP timings ranged from $N=1$, for vulnapp, for which only a single clean baseline run completed without transient network retries, to $N=6$ for DVWA and Juice Shop; and the Bash-versus-OPA gate latency benchmark in Table~\ref{tab:gate_benchmark} was collected over $N=30$ runs of each approach on identical input to obtain a stable mean and standard deviation. We report these $N$ values explicitly throughout rather than implying uniform statistical power across every measurement, and the single-run vulnapp ZAP figure is flagged as such wherever it is used in later analysis.

It is important to state plainly that ZAP was operated in passive baseline mode (\texttt{zap-baseline.py}) throughout this study, meaning it inspected traffic and default page responses without issuing active attack payloads. This is a deliberate and honestly reported scope limitation, discussed further in Section~\ref{sec:validity}, and it directly explains why the DAST findings in Table~\ref{tab:zap_findings} record zero High-severity alerts even against DVWA, an application with 254 Critical-severity container CVEs in Table~\ref{tab:cve_breakdown}.

Because the OPA gates are configured as hard-blocking gates -- any single gate failure halts the pipeline immediately and prevents the deployment stage from executing -- the ZAP DAST stage cannot be reached in a standard enforcement run in which any application fails the Configuration or Severity Gate. Accordingly, ZAP measurements and DAST findings reported in this paper were collected in dedicated DAST measurement runs in which the target application containers had been successfully built and deployed for testing purposes, with the blocking enforcement gates bypassed for that specific measurement purpose. The ZAP results therefore characterize DAST coverage and latency independently of the enforcement outcome of the blocking OPA gates. The enforcement outcomes (BLOCK/PASS decisions for each gate and each application) are reported separately in Table~\ref{tab:opa_gates} and reflect the full enforcement pipeline.

Fig.~\ref{fig:jenkins_stage} shows the Jenkins Stage View recorded across 19 consecutive pipeline builds during the evaluation period.

\centering

\caption{Jenkins stage view displaying 19 consecutive runs. Build \#19 shows ZAP DAST vulnapp taking 10min 19s due to cold-cache image pulling. Under warm-cache conditions, the Trivy scanning stages complete in single-digit seconds per application, while OPA gate evaluation runs in tens of milliseconds.}

The stages visible in Fig.~\ref{fig:jenkins_stage} correspond directly to the five pipeline layers described in Section~\ref{sec:arch}, with the parallel Trivy-and-OPA block rendered as a single fork-join step in the Jenkins user interface. Under warm-cache conditions, the Trivy scanning stages complete in single-digit seconds per application (3.9s--6.9s across the three targets, per Table~\ref{tab:timings}), while OPA gate evaluation runs in tens of milliseconds; together these stages are small relative to the ZAP stages that dominate wall-clock time elsewhere in the same view. Build~\#19's anomalous 10-minute-19-second ZAP vulnapp duration is not a gate malfunction but a cold-cache artifact, attributable to first-run container image pull overhead rather than to the DAST scan itself, and its presence in the 19-build sample is a useful reminder that infrastructure-level variance, distinct from tool-level variance, can dominate an individual run's wall-clock time. Excluding that cold-cache outlier, the remaining 18 builds are broadly consistent with the per-application ZAP means reported in Table~\ref{tab:timings}. The operational implication is that image pre-pulling or a warm local registry mirror is a prerequisite for the steady-state timings this paper reports, and its absence should be treated as a distinct, addressable source of pipeline latency rather than folded into the DAST cost itself.

\section{Results}
\label{sec:results}

\subsection{RQ1: Security versus Velocity}
Table~\ref{tab:timings} reports pipeline stage timings across repeated runs. The unsecured baseline pipeline, with all security stages removed, completes in a mean of 206.0 seconds ($N=5$, SD 53.1s, 95\% CI $[140.1, 271.9]$). Adding the full security stack -- Trivy, the OPA gates, and synchronous ZAP -- brings the observed full pipeline to an average of 229.0 seconds, an addition of approximately 23 seconds over baseline on a warm cache. Crucially, this whole-pipeline delta sits within the baseline's observed measurement variance (baseline SD is 53.1s) and therefore should not be presented as a statistically clean estimate of security-induced overhead. Instead, the RQ1 argument relies primarily on the per-stage decomposition in Table~\ref{tab:timings} and Fig.~\ref{fig:pipeline_timing}, identifying ZAP as the dominant latency contributor. This decomposition isolates the single-digit-second Trivy stage times and the minimal OPA latency from the 49--72-second cost of ZAP.

Fig.~\ref{fig:pipeline_timing} plots the mean execution time of each pipeline stage side by side, and the visual asymmetry it depicts is the central finding of RQ1: the Trivy and OPA stages are barely visible on the same axis as the ZAP bars, since their combined contribution is measured in single-digit seconds while ZAP's per-application means range from 49.0 to 72.0 seconds in Table~\ref{tab:timings}. The DVWA ZAP measurement carries a wide 95\% confidence interval of $[33.5, 110.5]$ seconds, reflecting genuine run-to-run variance in scan duration rather than measurement noise, plausibly driven by the number of HTTP endpoints DVWA exposes relative to the other two targets. When ZAP is decoupled from the synchronous critical path and instead run as an asynchronous nightly job, the developer-blocking overhead falls to under 15 seconds, which corresponds to a multiplier below approximately 1.07$\times$ over the 206-second baseline (compared with the roughly 1.11$\times$ multiplier, 229.0s / 206.0s, observed when ZAP runs synchronously within the full build). This decoupling recommendation, elaborated in Section~\ref{sec:discussion}, is the single largest lever available for reconciling RQ1's security requirement with developer velocity, and Fig.~\ref{fig:pipeline_timing} makes visually explicit why: ZAP, not container scanning and not policy evaluation, is the pipeline's latency bottleneck.

Taken together, these results answer RQ2 within our case-study scope: vulnerability profiles differ substantially across the evaluated application types, and base-image staleness dominates OS-layer CVE exposure, but this pattern is conditional on base-image age and technology stack rather than a universal property of container scanning.

\section{Discussion}
\label{sec:discussion}

Three operational recommendations follow directly from the results in Section~\ref{sec:results}.

First, decouple ZAP to a nightly staging job. Section~\ref{sec:results} showed that ZAP is the dominant contributor to the pipeline's synchronous overhead, and that removing it from the developer-blocking critical path reduces the effective overhead from the observed 229.0-second full pipeline average to under 15 seconds, a multiplier below approximately 1.07$\times$ over the 206-second baseline. This does not remove DAST coverage from the system, only its position on the critical path; the nightly job still runs against the most recently built image and still feeds the same Grafana dashboard shown in Fig.~\ref{fig:grafana_dashboard}.

Second, prioritize base-image updates for images with high operating-system-layer attribution, such as DVWA. Table~\ref{tab:layer_attribution} showed that 100.0\% of DVWA's CVEs originate in its end-of-life base image, meaning dependency-level patching has, by construction, zero effect on its CVE count. The directional comparison in Fig.~\ref{fig:base_freshness} illustrates that within our three-application case study, older end-of-life base images carry substantially larger OS-layer CVE counts, motivating teams to treat base-image replacement as the primary effective remediation rather than investing engineering effort in application-layer patches that cannot reduce the underlying OS-layer count.

Third, use OPA for any gate expressing more than one policy rule. Table~\ref{tab:gate_benchmark} showed that Bash-and-\texttt{jq} implementations grow 2.2$\times$ in lines of code per additional rule, while the equivalent Rego policy grows by only 3 lines, and that OPA's structured JSON output additionally enables the persistent audit trail visualized in Fig.~\ref{fig:grafana_dashboard}. A single-rule gate may reasonably remain a Bash script; a gate expected to accumulate rules over time, as most production security gates eventually do, should be built in OPA from the outset.

The observability layer shown in Fig.~\ref{fig:grafana_dashboard} is what a bare Bash exit-code gate structurally cannot provide: a persistent, queryable time series of CVE severity trends, OPA configuration violation counts, and per-stage pipeline latency across historical builds, rather than a single pass-or-fail signal visible only in a transient console log. This distinction matters operationally because it allows a team to answer questions a Bash script cannot -- for instance, whether Critical CVE counts are trending upward across successive builds, or whether a particular gate's latency is degrading over time -- without re-parsing historical console output line by line. The dashboard's persistence is a direct consequence of OPA's structured JSON output described in Section~\ref{sec:results}: Prometheus can scrape and retain structured fields from every build run, whereas a Bash exit code of 0 or 1 carries no fields to retain beyond the binary outcome itself.

\section{Threats to Validity}
\label{sec:validity}

Several limitations should temper how the results reported above are generalized. All timing measurements were collected on a single host, so the absolute wall-clock figures in Table~\ref{tab:timings} may not transfer directly to differently provisioned CI infrastructure, although the relative ordering of stages, and in particular ZAP's dominance as the slowest stage, is expected to be robust to host changes given the magnitude of the gap between ZAP's and Trivy's mean durations. The study evaluates only three applications, chosen deliberately to span a range of base-image freshness and technology stack rather than to be statistically representative of any broader application population, so the layer-attribution percentages in Table~\ref{tab:layer_attribution} should be read as illustrative of a mechanism rather than as population-level estimates that would generalize to an arbitrary fourth application.

ZAP was run exclusively in passive baseline mode, without active attack payloads, and this is why Table~\ref{tab:zap_findings} records zero High-severity alerts even against DVWA; an active ZAP scan would very likely surface additional, higher-severity findings that this study did not measure and cannot claim. Relatedly, ZAP's sample sizes range from $N=1$ for vulnapp to $N=6$ for DVWA and Juice Shop, considerably smaller than the $N=30$ Bash-versus-OPA benchmark in Table~\ref{tab:gate_benchmark}, and the single-run vulnapp ZAP figure in particular should be read as one observation rather than a stable mean with an associated confidence interval.

An inner-team annotation exercise was conducted to assess the reliability of Trivy-based severity classifications underlying Tables~\ref{tab:cve_breakdown}, \ref{tab:layer_attribution}, and \ref{tab:opa_gates}. Fifty CVEs were randomly sampled from the vulnapp Trivy report and independently annotated by the two developers of this project, Saurabh Pandey (Rater~1) and Aniket Kumar (Rater~2), each classifying every sampled finding as a true positive or false positive against the NVD database description without consulting the other rater. The two raters are the paper's authors, which constitutes a potential conflict of interest that must be stated explicitly: as domain-familiar annotators rather than independent external judges, they may share implicit priors about the codebase that inflate agreement beyond what an external rater would achieve. To mitigate this, classification was performed under a blind protocol with a predefined rubric, and raters did not discuss findings before submitting independent labels. The raw observed agreement was $P_o = 84.0\%$ (42 of 50 findings). The chance-agreement probability was $P_e = 0.529$, giving
\begin{equation}
\kappa = \frac{P_o - P_e}{1 - P_e} = \frac{0.840 - 0.529}{1 - 0.529} = 0.660,
\label{eq:kappa}
\end{equation}
corresponding to Substantial Agreement on the Landis and Koch scale~\cite{ref12}. This result should be read as an inner-team annotation reliability check demonstrating that the two developers consistently agreed on how to interpret Trivy's severity output against NVD descriptions, not as externally validated construct validity. Independent external raters would be required to make a stronger claim, and we identify this as a priority for future work.

\section{Conclusion and Future Work}
\label{sec:conclusion}

This paper set out to design, implement, and empirically evaluate a five-layer DevSecOps pipeline that embeds SAST, SCA, container scanning, Policy-as-Code gating, and DAST into a single Jenkins pipeline, and to answer three research questions about the resulting system. All five stated project deliverables were achieved over the course of this work: a fully scripted Jenkinsfile enforcing security gates and configurable thresholds was implemented and evaluated across nineteen consecutive builds (Fig.~\ref{fig:jenkins_stage}); an OPA policy bundle covering configuration compliance, CVE severity thresholds, and cross-tool CVE provenance was written and unit-tested with \texttt{opa test}; the pipeline was evaluated end-to-end across three open-source target applications spanning a deliberate range of base-image freshness (Table~\ref{tab:targets}); a Prometheus- and Grafana-backed security metrics dashboard was deployed and populated with live pipeline data (Fig.~\ref{fig:grafana_dashboard}); and this paper itself constitutes the research write-up presenting the resulting trade-off model and configuration recommendations.

RQ1, the security-versus-velocity cost of embedding security tooling into a CI/CD pipeline, is answered within our single-host case study by the Table~\ref{tab:timings} measurements and Fig.~\ref{fig:pipeline_timing}: the observed full synchronous pipeline average was 229.0 seconds versus a 206.0-second baseline; however, the 23-second whole-pipeline delta lies within the baseline's observed variance and should not be interpreted as a statistically clean overhead estimate, and decoupling the ZAP DAST stage to an asynchronous job reduces the developer-blocking cost to under 15 seconds, a multiplier below approximately 1.07$\times$ over the baseline, identifying DAST rather than container scanning or policy evaluation as the dominant latency contributor. RQ2, on how container vulnerability profiles differ across application types and whether base-image staleness dominates CVE exposure, is answered by the layer-attribution results in Table~\ref{tab:layer_attribution} and the illustrative comparison in Fig.~\ref{fig:base_freshness}: within our case study, base-image staleness dominates OS-layer CVE exposure conditionally -- DVWA's 100.0\% operating-system-layer attribution reflects its end-of-life base image, while Juice Shop's 87.1\% application-layer attribution shows that the same pattern does not hold for actively maintained images. RQ3, on whether Policy-as-Code provides measurable advantages over equivalent Bash scripting, is answered in our local environment by the OPA-versus-Bash benchmark in Table~\ref{tab:gate_benchmark} and the inner-team annotation reliability check in Section~\ref{sec:validity}: OPA showed a 42.8\% lower mean evaluation latency than Bash in our $N=30$ benchmark, while the LOC comparison suggests more favorable scaling as rules accumulate, and produces structured output that provides practical auditability advantages that a bare exit code cannot, while the $\kappa = 0.660$ result supports consistent interpretation of the severity classifications that feed its gates.

Future work includes extending policy enforcement into the Kubernetes admission-control layer using Kyverno, so that the same Policy-as-Code discipline applied at build time in this paper also governs runtime deployment decisions; generating Software Bill of Materials (SBOM) artifacts in CycloneDX format alongside each build to make the dependency graph underlying Tables~\ref{tab:cve_breakdown} and~\ref{tab:layer_attribution} independently auditable outside the pipeline itself; adding secret-scanning coverage via TruffleHog, a gap not addressed by any of the five layers evaluated in this study; running ZAP in active rather than passive-only mode to test whether the zero-High-alert result in Table~\ref{tab:zap_findings} holds under genuine attack payloads; and exploring tiered, per-team OPA severity thresholds rather than the single global threshold used throughout this study, to accommodate teams operating at different points on the latency-versus-auditability trade-off that motivates the Provenance Gate design described in Section~\ref{subsec:comparative}.

All code, Jenkinsfiles, OPA policies, scan results, and timing data from this study are publicly available at \url{https://github.com/Saurab2h/ieee-devsecops-project}.
